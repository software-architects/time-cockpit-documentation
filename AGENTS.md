# AGENTS.md

Agent-facing guide for this repository. Works with Claude Code (via `@AGENTS.md` in `CLAUDE.md`), Codex, Cursor, Copilot and similar tools. Keep it short; put long-form standards in `specs/`.

## What this repo is

The DocFX source for <https://docs.timecockpit.com>, the product documentation of time cockpit (time tracking SaaS).

| Path | Purpose |
|------|---------|
| `doc/**` | All product documentation as Markdown, one folder per topic. Main navigation: `doc/toc.yml`. |
| `api/` | API reference YAML, generated by DocFX from `../Binaries/TimeCockpit.Data*.dll`. Do not edit by hand. CI builds with `-SkipMetadata` and uses the committed files. |
| `.config/dotnet-tools.json` | Local dotnet tool manifest that pins the docfx version used locally and in CI. |
| `tctemplate/` | Custom layer on the built-in DocFX `modern` template: `public/main.css` (brand tokens, fonts, navbar), `public/main.js` (options, Mermaid zoom), `layout/_master.tmpl` (copy of the modern layout plus canonical/hreflang tags; re-diff against `dotnet docfx template export modern` on every docfx upgrade). |
| `specs/` | Planning notes and content standards, not published. |
| `tools/GenerateLlmsTxt/` | PowerShell script that generates `llms.txt` and `llms-full.txt`. |
| `tools/GenerateRedirects/` | C# console app that maintains IIS redirect data. |
| `App_Code/`, `App_Data/`, `web.config` | IIS hosting and URL redirects. Maintained manually. |
| `_site/` | Build output. Gitignored, never commit. |

Content language is English. Hub pages (`doc/for-users.md`, `doc/for-developers.md`) and role FAQs (`doc/*-faq.md`) sit at the top of `doc/`.

## Build and preview

CI is the classic (non-YAML) Azure DevOps build pipeline `TimeCockpit.Documentation-CI`, defined in the Azure DevOps UI, not in this repo. Its steps: Use .NET SDK 10.x, then a PowerShell task running `.\build.ps1 -SkipMetadata`, then Archive `_site`, then Publish Artifact `site`. Any change to the build order must be made there as well. The docfx version is pinned in the local tool manifest `.config/dotnet-tools.json`; `build.ps1` runs `dotnet tool restore` and then `dotnet docfx`, so CI and local builds use the same docfx and the built-in `modern` template. To upgrade docfx, change the version in the manifest, run `dotnet tool restore` and `dotnet docfx template export modern`, re-diff `_exported_templates/modern/layout/_master.tmpl` against `tctemplate/layout/_master.tmpl` and port upstream changes, then build and compare the output. Locally and in CI, always build with the wrapper script, never with a bare `docfx` or `dotnet docfx` call:

```powershell
.\build.ps1                 # docfx metadata + build, then llms/markdown publish
.\build.ps1 -SkipMetadata   # no ../Binaries needed, skips API reference generation
.\build.ps1 -Serve          # additionally starts a local preview
```

`build.ps1` first runs `tools\GenerateSiteIndex\generate-site-index.ps1` (regenerates the committed `doc/all-pages.md`, a server-rendered link list of every page for crawlers that do not execute the JavaScript navigation; never edit that page by hand), then `dotnet tool restore`, then `dotnet docfx docfx.json`, then `tools\post-build.ps1`, which runs `tools\GenerateLlmsTxt\generate-llms.ps1` and then `tools\FixSitemap\fix-sitemap.ps1` (rewrites sitemap `lastmod` with each page's last Git commit date and removes `_noindex` pages from the sitemap; needs git and full history, a shallow clone falls back to the build time). The llms step regenerates `llms.txt` / `llms-full.txt` and copies `doc/**/*.md` into `_site`. The raw `.md` files are not part of the regular DocFX output, but `llms.txt` links to them, so a deploy without this step yields 404s for every Markdown link.

`llms.txt` and `llms-full.txt` are generated **and** committed. Never edit them by hand. IIS additionally needs a `.md` MIME mapping in `web.config` (`text/markdown; charset=utf-8`) to serve the files.

## Content conventions

- Every page starts with front-matter containing `title` and `description`. The description feeds `llms.txt` and the meta description, so make it a real one-sentence summary of at most 155 characters; quote it when it contains a colon. Optional keys: `faq: true` (page is an FAQ, every `###` question becomes schema.org FAQ markup), `og_image: name.png` (social preview image under `images/`, 1200x630, default `og-default.png`), `_noindex: true` (keeps the page out of search engines).
- Exactly one H1 per page (the `#` heading right after the front matter); sections start at `##`.
- Cross-folder links use `~/doc/...` (for example `[TCQL Overview](~/doc/tcql/overview.md)`). Never use `../` relative paths.
- File, folder and image names are kebab-case. No page name may end with `index.md`: the IIS redirect module (`App_Code/TimeCockpit/UrlRedirect`) sends every request path ending with `index.html` to the overview page. Article images live in an `images/` folder next to the article (for example `doc/mcp/images/`).
- A new page must be added to `doc/toc.yml`, otherwise it is unreachable from navigation.
- Use DocFX alerts: `> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`.
- Release notes are one file per month: `doc/release-notes/YYYY-MM.md`.
- Pages under `doc/mcp/` carry a "Preliminary documentation" warning banner. Keep it until the feature is released.
- Videos are consent-gated. Never paste a raw YouTube/Vimeo iframe. Use `<div class="tc-video" data-youtube="ID" data-title="..." data-poster="images/video-posters/ID.jpg"></div>` (or `data-vimeo="ID"`); `tctemplate/public/main.js` renders a local poster/placeholder until the visitor accepts "External Media" in the cookie banner. Store posters locally, never link a third-party thumbnail.
- Privacy: Google Analytics is loaded only after consent (Silktide banner configured in `tctemplate/layout/_master.tmpl`); Simple Analytics is cookieless and always on. Do not add other third-party scripts, fonts or embeds without a consent gate.
- Links to the marketing site are absolute (`https://www.timecockpit.com/features/...`, `https://www.timecockpit.com/blog/...`). Verify the slug exists before linking.
- UI navigation paths follow the real app modules: "Management" (not "Data Exchange"), "User" (not "Employee Time Tracking"). See `specs/ai-generated-content.md`.

## German documentation

The product documentation exists in English (`doc/`, site root) and German (`de/doc/`, published under `/de/`). The API reference stays English.

- `de/docfx.json` is a second docfx build into `_site/de` (own navbar `de/toc.yml`, own search index, German UI strings from `de/tctemplate-de/token.json`); `build.ps1` runs it after the English build, the pipeline needs no change.
- German URLs use translated slugs: folder names from `tools/Translate/folders.de.json`, file names as kebab-case ASCII of the German title (`ae`, `oe`, `ue`, `ss`). Every German page carries `en_page: doc/<english path>.md` in its front matter; that key is the only link between the two languages (hreflang, language switch, navigation).
- Links inside German pages are copied verbatim from the English source and resolved by `tools/Translate/relink-de.ps1` (before every build): translated targets become `~/doc/<german path>.md`, untranslated ones `/doc/<english path>.html`. Images: a German screenshot under `de/doc/<folder>/images/` wins, otherwise the English image root-absolute (`/doc/<folder>/images/<name>`). Never hand-write `/de/` URLs in Markdown.
- `de/doc/toc.yml` is generated by `tools/Translate/build-de-toc.ps1` from `doc/toc.yml` and the names in `tools/Translate/toc.de.json`; entries without a German page link to the English page with the suffix "(EN)". Edit `doc/toc.yml` or `toc.de.json`, never the generated file.
- `tools/FixHreflang/fix-hreflang.ps1` (post-build) adds the `hreflang` pair, `og:locale:alternate` and the language switch targets to both pages of every pair.
- Translating a page: follow `tools/Translate/translate-page.md` and the glossary `tools/Translate/glossary.de.md` (UI labels as in the German product UI, "time cockpit" unchanged and lowercase, formal "Sie"); keep code blocks, TCQL, entity and property names, alert markers and video placeholders unchanged; translate `title`, `description` (max. 155 characters), `keywords`; copy `faq`, `_noindex`, `og_image`.

## Accuracy rules

This documentation is a source of truth for customers and for AI assistants (llms.txt, context7). Wrong details are worse than missing details.

- Never invent TCQL functions, entities, properties, lists or actions. Only reference TCQL functions documented under `doc/tcql/`, and only `APP_*` / `SYS_*` names that exist in the data model.
- Code samples must be tested or copied from working code. Include the scenario and the expected result.
- If you are not sure a feature exists or behaves as described, leave it out or ask, rather than guess.
- Detailed standards, templates for entity/list/workflow pages and past lessons learned: `specs/ai-generated-content.md`.

## Do not touch

- `_site/`, `obj/`, `_exported_templates/` (build output)
- `api/**.yml` (generated)
- `llms.txt`, `llms-full.txt` (generated, regenerate via script)
- `App_Code/`, `App_Data/`, `web.config` (IIS hosting, changed manually by the owner)

## Agent workflow and delegation

- **Fable** (main session): high-level exploration, requirement refinement, planning, and final review of the result.
- **opus-implementer** (subagent, defined in `.claude/agents/opus-implementer.md`): mechanical execution of an approved plan, writing and editing pages, updating `doc/toc.yml`, running the build and the llms script, and reporting build errors verbatim.

Plan first, then hand the concrete file-level changes to the implementer, then review.
